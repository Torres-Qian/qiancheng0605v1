# 重构假设说明

> V2 下单流程异步事件驱动重构 — 架构设计决策与容量规划

---

## 1. 为什么选择异步事件驱动，而不是继续同步处理

### 问题分析

当前 V2 系统采用同步阻塞模式：用户上传文件 → 解析 → 规则引擎 → 逐行校验 → 逐行 INSERT → 返回响应。这个流程在小文件场景（几十行）下表现良好，但在以下场景会迅速失效：

- **大文件超时**：10,000 行数据即使每行仅耗时 200ms，全流程也需 30+ 分钟，远超 Vercel Serverless 的请求超时限制
- **连接池耗尽**：逐行查询 SKU + 逐行 INSERT 会瞬间耗尽数据库连接池
- **用户体验差**：用户只能看到 loading，无法感知进度
- **故障定位困难**：批量导入部分失败时，无法快速定位具体行和字段

### 选择异步事件驱动的理由

1. **上传即返回**：用户上传后立即拿到 task_id，不等待后台处理，P95 ≤ 1 秒
2. **弹性伸缩**：Worker 可独立部署在 Railway/Render 等平台，不受 Vercel Serverless 限制
3. **批量处理**：收集批次内所有 SKU 后一次性查询，1000 行一次性 UPSERT，数据库压力可控
4. **可观测性**：每个任务、批次、行级错误都有 traceId 贯穿，故障 1 分钟内定位
5. **任务可恢复**：队列支持重试，Outbox 保证消息不丢失，卡死任务可自动恢复

### 何时同步反而更简单可靠

- 小文件（≤ 100 行）：同步处理开销更小，延迟更低
- 需要立即返回结果的场景（如预览解析）
- 单条记录的实时校验

## 2. 处理单元大小如何设计，为什么这样设计

### 选择：1000 行/批

| 因素 | 分析 |
|------|------|
| **重试成本** | 1000 行失败重试成本适中；过小（如 100 行）会创建 100 个批次，Outbox 写入开销大；过大（如 5000 行）单次失败影响面大 |
| **内存占用** | 1000 行运单数据内存约 500KB，Worker 内存安全 |
| **数据库性能** | 1000 行一次性 UPSERT 约 200ms，数据库连接占用时间短 |
| **并发效率** | 10,000 行 = 10 个批次，2 Worker 并发消费，理论 2 秒完成 |
| **可观测性** | 每批独立记录性能日志，便于发现慢批次 |

---

## 3. Worker / Consumer 的容量规划

| 项目 | 配置 | 说明 |
|------|------|------|
| Worker 数量 | 2 | 并发消费 Job |
| 单 Worker 并发 | 1 Job/Worker | 避免数据库连接池耗尽 |
| 最大并发 Job 数 | 4/秒 (limiter) | 防止瞬间大量 Job 涌入 |
| 部署平台 | Railway / Render | 常驻进程，不受 Vercel 限制 |
| 失败重试 | 3 次，指数退避 | 2s → 4s → 8s |

---

## 4. 10,000 单/分钟的性能推导

### 耗时拆解（单批次 1000 行）

| 阶段 | 操作 | 预估耗时 |
|------|------|----------|
| 文件解析 | xlsx 读取 + 字段映射 | ~100ms |
| 规则引擎 | 类型转换、默认值等 | ~50ms |
| SKU 批量校验 | `IN (...)` 查询 1000 个 SKU | ~30ms |
| 行级校验 | 必填/格式/电话等内存校验 | ~10ms |
| 批量 UPSERT | `insert().values().onConflictDoUpdate()` | ~200ms |
| 单批次总计 | | ~400ms |

### 10,000 行全链路计算

- 批次数：10,000 / 1000 = 10 批
- 2 Worker 并发消费
- 理论总耗时：10 / 2 × 400ms = 2000ms = **2 秒**
- 实际考虑网络延迟 + 队列开销：预估 **5~15 秒**
- 远低于 60 秒目标

## 5. 数据库连接池和 Worker 并发如何控制

- Worker 并发 = 2，每个 Worker 同时处理 1 个 Job
- Neon PostgreSQL 连接池默认 20 个连接
- 每个 Worker 批量操作仅占用 1 个连接，峰值连接数 ≤ 5
- 使用 `limiter: { max: 4, duration: 1000 }` 限制每秒最多 4 个 Job

---

## 6. Outbox 如何避免"任务创建成功但消息丢失"

采用 **Transactional Outbox** 模式：

1. 上传 API 在一个数据库事务中完成：
   - INSERT import_tasks（创建任务）
   - INSERT import_task_batches × N（创建批次状态记录）
   - INSERT event_outbox × N（写入待投递事件）
   - INSERT trace_events（记录链路事件）
2. 事务提交后，所有记录同时生效
3. 独立的 Outbox Dispatcher 轮询 `event_outbox` 表
4. 将 status='pending' 的事件投递到 BullMQ 队列
5. 投递成功后更新 status='sent'
6. 即使服务宕机，重启后 Dispatcher 继续轮询未投递事件

## 7. 处理单元 Job 如何做到幂等

1. **批次状态检查**：Worker 消费 Job 后，首先检查 `import_task_batches` 中该 unit_id 的状态
2. **已完成跳过**：若 status='COMPLETED'，直接返回 `already_completed`
3. **唯一业务键**：`waybills` 表使用 `(external_order_no, sku_code, line_no)` 作为去重键
4. **UPSERT**：`onConflictDoUpdate` 保证重复写入不会产生新记录
5. **原子进度更新**：使用 `processed_rows + N` 原子增减，避免重复累计

## 8. 部分行失败时为什么允许成功行继续入库

- **业务价值**：10,000 行中 9,995 行成功，5 行失败。如果整体回滚，用户需要修复 5 行后重新导入全部 10,000 行，时间成本极高
- **错误可修复**：失败行详细记录在 `import_task_errors`，用户可针对性修复后重新导入
- **状态清晰**：任务状态为 `PARTIAL_SUCCESS`，前端明确展示成功/失败数量
- **行业实践**：批量数据导入系统（如电商 ERP）普遍采用"成功先行、失败记录"策略

## 9. SKU 校验降级的触发条件和风险提示

### 触发条件

- SKU 主数据查询超时超过 3 秒
- 数据库连接短暂不可用

### 降级行为

- 跳过 SKU 主数据校验，仅做本地格式校验（必填、电话格式等）
- 所有 SKU 标记为有效
- 任务标记 `degraded=true`
- 前端显示黄色警告横幅

### 风险提示

- 前端明确展示："SKU 校验已降级：本次导入未经过商品主数据完整校验，数据可能需要后续复核"
- 降级状态写入 trace_events
- 服务恢复后新任务自动恢复完整校验
- 不对已降级任务做自动补校验（避免对已入库数据产生二次影响）

## 10. 错误日志中敏感数据如何脱敏

使用 `src/lib/utils/mask.ts` 工具：

- **手机号**：保留前 3 位和后 4 位，中间替换为 `****`。例如 `13812345678` → `138****5678`
- **地址**：保留前 6 个字符，其余替换为 `****`
- **其他字段**：不脱敏，保留原始值用于排障
- **脱敏时机**：写入 `import_task_errors` 前对敏感字段调用 `maskValue()`

## 11. 压测数据如何生成、如何清理

### 生成

- 运行 `npx tsx scripts/seed-data.ts`
- 自动清理 `sku_master` 表并插入 20,000 条
- 生成 `test-data/10000-orders.xlsx`（10,000 行 + 故意插入的非法数据）

### 清理

- SKU 主数据：脚本每次执行先 `TRUNCATE`，确保幂等
- 压测文件：覆盖写入 `test-data/10000-orders.xlsx`
- 导入任务数据：通过数据库手动清理或设置 TTL
